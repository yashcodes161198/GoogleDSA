# Production comparison procedure

The user requested a before-deployment run and will ask for the after-deployment run later. Do not deploy or schedule a rerun from this instruction. Before data is in `output/performance-2026-10-09/prod-before-brave.json`; conclusions and measurement limits are in [PERFORMANCE.md](PERFORMANCE.md).

Use the same signed-in Brave profile through `mcp__cua_repl`, the same computer/network and viewport (2175 × 1044 where practical). Keep normal cache behavior. Record changed catalog size, progress, queue, viewport, connection or browser/tool version; do not manufacture matching progress. Before had 682 catalog questions, ten revision rows, zero revised today and 50-row Problems pagination. Verify that production script filenames changed after deployment; do not assume the local branch was deployed. Do not replace before artifacts.

Measure wall clock in the CUA JavaScript session (`Date.now()` before the click/reload, after target readiness). This includes extension/action/locator overhead and cannot be called paint, INP, network or database duration. Do not use an outside browser automation library or copy auth tokens. The extension's page scope did not expose `performance` during the before run.

1. Inspect the signed-in page, filters and selected page size. Set up Problems, then Revise, and report these initial navigations separately. Before setup timings were 3221 and 3131 ms. Keep subsequent samples separate from these warmups.
2. On loaded Revise, time five pairs of already-visible readiness waits. Time three same-page Revise link clicks plus the same waits as extension overhead controls (before performed these clicks after the navigation round trips and first reload). Do not subtract controls from the measured flows.
3. From Revise, perform ten Problems → Revise round trips. Each Problems sample clicks the exact Problems nav link, waits for the exact Problems heading, then waits for the visible table row containing Longest Palindromic Substring. Each Revise sample clicks the exact Revise nav link, waits for Daily revision, then waits for Replace revised questions. Record round, destination and elapsed milliseconds. These are 20 samples, ten per destination. Inspect headings/content after actions; only proceed when the expected target is visible.
4. Measure five warm document reloads per page using the same readiness targets. Before captured one Revise reload before favorite checks and four afterward, then five Problems reloads. Report reloads separately from client navigation and from cold first visits.
5. Test a reversible favorite on a question already in the revision queue (before: Minimum Knight Moves, originally false). Capture original state. Start timing, click its favorite, wait for the opposite button label, and record feedback time. Then wait until Replace revised questions is enabled and record transition-settled time. This is a UI signal, not exact durable-write acknowledgement. Reload and verify persistence, then restore the original favorite and verify again after reload and in Problems search. Collect at least four complete timings with paired toggles; leave the original state restored. Do not mark solves/revisions or change timer values to create performance samples. Before's five retained feedback samples and four settled samples include two interrupted timing attempts, recorded in the raw JSON.
6. Check search for the favorite target, difficulty filtering (it is Medium, so Hard should exclude it), and 25-row pagination. Inspect default DOM count at 50 rows, then All-mode count, then restore 50. Read labels from actual page state; label text includes option text, so `getByLabel('Difficulty')` with partial matching worked while exact matching did not. If All stalls the extension, inspect state before retrying; CSS `main select` index four was the observed Rows per page select in the before DOM. Verify filter values ALL,ALL,ALL,ALL,50 and empty inputs. Record console warnings/errors separately from tool failures.
7. Save raw results as `output/performance-2026-10-09/prod-after-brave.json` with the same schema and run `node output/performance-2026-10-09/summarize-prod.mjs prod-after-brave`. Compare per-flow medians, ranges, sample counts and overhead controls. Do not compare extension timings to loopback proxy timings. Report any data/conditions change and any missing samples. A small warm sample is not a production percentile SLA.

For saves, a single locator wait may hit the extension's approximately three-second deadline even with a larger requested timeout. Before recovery checked the actual enabled state, attempted a CSS readiness wait, inspected again on a timeout and retried up to five bounded waits. Never repeat a mutation merely because its readiness wait timed out; first inspect the actual favorite and pending state. If restoration fails, finish restoring and verify it before concluding the run.

The baseline is a functional and automation-observed readiness test. A browser Performance/Network trace and server/SQL timings would be additional evidence, requiring a tool that exposes those metrics. The current measurements do not attribute the production wait to a particular database query or promise the local speedup will transfer unchanged to Vercel.
